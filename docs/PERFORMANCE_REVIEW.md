# Проверка замечаний о производительности — 31 октября 2026

Проверен текущий рабочий код, включая уже находившиеся в папке изменения.
Основные механизмы из приложенного ревью подтвердились. Число компиляций
RegExp, задержки записи и влияние на FPS в исходном тексте не измерены:
вызов конструктора RegExp сам по себе не доказывает новую компиляцию.

| Замечание | Проверка и исправление |
| --- | --- |
| Статистика перечитывает журнал каждые 15 секунд | Таймер удалён. Первый снимок читается один раз; JSON остаётся в отдельном рабочем изоляте до закрытия страницы. Изменение события передаёт только его ID и актуальный payload. Удаления, обновления одной записи, откаты транзакций и внешняя синхронизация проверены. Смена периода не перечитывает журнал. Цели получают дневные итоги из `audio_daily_totals_v1` плюс внешний журнал. |
| Все типы записей сортируются по title | `Repository.records` сортирует по названию только книги. Восстановление получает `DISTINCT bookId` в SQL. Табличный sidecar запрашивает события конкретной книги через индекс. Управление статистикой использует одну загрузку старых сессий вместо двух. |
| Позиция перестраивает весь плеер | Отдельный `playbackPosition` обновляет ползунки, время, прогресс книги и мини-плеера. Изменения состояния и трека по-прежнему уведомляют страницу. Списки глав на широком экране и в телефонной панели создаются лениво. |
| SQLite без WAL | При открытии включён WAL. Сохранён стандартный `synchronous=FULL`: переход на NORMAL ослабил бы сохранность последних подтверждённых записей при потере питания. Проверено `VACUUM INTO` при наличии записей в WAL. |
| Журнал не использует частичный индекс | Для событий запрос повторяет `SchemaSql.audioEventRows` и `audioEventBook`. `EXPLAIN QUERY PLAN` реального запроса подтверждает `records_audio_day_v2`. Повреждённый JSON пропускается. Индекс сужает выборку по книге; сортировка её событий по времени всё ещё может использовать временное дерево. |
| Полки повторяют фильтрацию и сортировку в build | Результат кешируется по данным и условиям. Выделение строки и смена сообщения используют кеш. RegExp вынесены в статические поля, поисковая строка приводится к нижнему регистру один раз; ввод объединяется задержкой 200 мс. Это файловые полки «Книги» и «Аудиокниги», а не личный архив. |
| Хеширование книг в UI | Обычный текстовый файл читается, проверяется SHA-256 и разбирается в одном изоляте. Для Android SAF чтение через платформенный канал остаётся в основном изоляте, затем байты передаются через `TransferableTypedData`. Проверка PDF и локальных обложек также вынесена из UI. Хеширование обложек сохранено, чтобы обнаруживать замену содержимого. |

Дополнительно переведены на `ListView.builder` корзина архива, заметки
Obsidian, аудиозаметки и история перемоток. Инициализация отключённого
облака проверяет наличие очереди и не выполняет два записывающих SQL
оператора на каждой локальной правке. Проверка состояния облака осталась:
кешировать её без учёта переключения транспорта и отката транзакций опасно.

Целевые сценарии:

Итоговый совместный прогон 19 тестовых файлов: **108 тестов прошли**.
`dart analyze lib` вместе с новыми и обновлёнными тестами: **No issues found**.
Лог прогона: `apps/pepehub/build/performance-review-tests.log`.

- 12 001 событие: один полный снимок при открытии; за 46 секунд без
  изменений новых запросов истории нет; замена и удаление события запрашивают
  только изменённые ID. Старые интервалы продолжают учитываться в итогах.
  Внешняя замена данных вызывает новый полный снимок; откат не меняет итогов.
- 100 событий позиции: 100 уведомлений прогресса и 0 уведомлений всей страницы;
  смена трека продолжает уведомлять страницу.
- 300 аудиофайлов: ограниченное количество построенных строк на телефоне
  и широком экране, с прокруткой до последней главы.
- Существующий масштабный сценарий: 500 текстовых книг, 500 аудиокниг,
  50 001 трек, 1000 карточек архива, ленивые списки и сетка. Архив создаёт
  3 начальные строки; файлы автоматически в архив не добавляются.
- Режим WAL, сохранение FULL и включение последних записей в резервную копию;
  восстановление старой базы, прогресса, заметок и журналов.

Полная история нужна аналитике повторов, серий и календаря. При первом
открытии она всё ещё загружается целиком, а расчёт в рабочем изоляте
проходит по истории при изменениях. Простое ограничение SQL выбранным
периодом нарушило бы эти показатели. Числа FPS и ускорение на реальном
Android-устройстве не измерялись; тестовые проверки не заменяют профилирование.
