# Протокол синхронизации v1 — реализованная часть

С версии приложения 0.4 допустимые `book.format`: `epub`, `fb2`, `txt`, `md`, `html`, `docx`, `rtf`, `pdf`, `audio`. Схема SQL и `schemaVersion: 1` сохраняются; FB2.ZIP учитывается как FB2. Сервер должен быть обновлён до отправки новых форматов. Старый сервер отвергает неизвестный формат, не удаляя локальную очередь клиента. Старые приложения рекомендуется обновить для правильного отображения этих записей.

Все пути `/v1/*` требуют `Authorization: Bearer <device-token>`. В D1 хранится SHA-256 ключа. Сервер получает ownerId и deviceId из записи устройства; ownerId от клиента не принимается. Отозванное устройство получает 401. Тело JSON ограничено 32 KiB. Кеширование ответов отключено.

## Методы

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /health | Публичный статус и schemaVersion, без данных |
| GET | /v1/me | Проверенные deviceId и ownerId |
| POST | /v1/operations | Одна операция; accepted либо conflict с серверной версией |
| GET | /v1/changes?after=0&limit=100 | Изменения владельца по серверной sequence, cursor, hasMore |
| POST | /v1/ack | Подтверждение локально применённого cursor конкретного устройства |

Лимит страницы 1–200. Порядок sequence глобален, поэтому между записями одного владельца могут быть пропуски. Курсор берётся из последней полученной записи, а не увеличивается на число записей. v1 не очищает журнал и не имеет snapshot endpoint.

## Операция

```json
{
  "schemaVersion": 1,
  "operationId": "11111111-1111-4111-8111-111111111111",
  "deviceId": "22222222-2222-4222-8222-222222222222",
  "entityType": "book",
  "entityId": "33333333-3333-4333-8333-333333333333",
  "baseRevision": 0,
  "action": "put",
  "payload": {
    "title": "Пример",
    "authors": ["Автор"],
    "format": "epub",
    "status": "planned"
  }
}
```

entityType: book либо session. Форматы book: epub/audio; статусы: planned/active/finished. Поля session определены и проверяются в `contracts/protocol.ts`: bookId, kind, startedAt, endedAt, activeSeconds, timezone, source. Начало/конец — UTC ISO с точностью до секунд или миллисекунд. Активное время не больше интервала; сессия ограничена семью днями. Микросекунды нормализуются клиентом до миллисекунд.

Создание использует baseRevision=0, изменение — текущую ревизию. Удаление: action=delete, payload=null, baseRevision>0. Tombstone не восстанавливается обычным put. Связанные сессии не удаляются каскадно: история сохраняется.

## Доставка и конфликты

Операция, результат, сущность и журнал фиксируются транзакцией `DB.batch()`. Сравнение ревизий выполняется в SQL внутри транзакции. Повтор того же operationId и нормализованного содержимого возвращает первоначальный результат даже после последующих изменений. Повтор ID с другим содержимым возвращает 409 `operation_id_reused`. Повторный конфликт также возвращает первоначальную конфликтующую версию; более новая доступна через журнал.

Неизвестные поля, недопустимые типы, даты/длительности, формат и ревизия возвращают 400. Несоответствие deviceId ключу — 403. Ошибки базы не возвращают клиенту SQL и персональные данные.

Клиент сохраняет optimistic records, remote_records и outbox. Последующие офлайн-правки одной сущности ожидают следующую ревизию. При конфликте остальные операции этой сущности блокируются, локальный текст остаётся. Серверные страницы обновляют remote_records; пользовательская версия records меняется только при отсутствии ожидающих операций. Страница и cursor применяются одной локальной транзакцией.

## Ограничения текущего этапа

- Ручной запуск синхронизации; нет фонового scheduler/backoff.
- Конфликт всей сущности; нет слияния по полям и действия «отправить мою версию поверх».
- Нет автоматической смены аккаунта или облачного provisioning устройств.
- Нет позиций EPUB/аудио, assets и файлового API.
- Локальные assets и аудиопозиции реализованы в схеме клиента v2, но не передаются протоколом v1.
- Локальная библиотека загружается целиком; пагинация UI/FTS ещё не внедрены.
- В журнале нет очистки; добавление retention возможно только вместе со snapshot/recovery.
- Данные SQLite-клиента и синхронизация проверены на тестовых данных, не на библиотеке пользователя.

Основание транзакционной модели: [Cloudflare D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/).

## Checkpoints аудио

Клиент может объединять последовательные checkpoints одной сессии, пока операция ещё ни разу не отправлялась. `freezeOperation` атомарно отмечает attempted=1 и читает окончательный payload непосредственно перед HTTP-запросом. После этого payload и operationId остаются неизменными при повторе, а новое состояние получает следующую операцию/ревизию. Миграция из локальной схемы v1 консервативно помечает все старые ожидающие операции как attempted.
