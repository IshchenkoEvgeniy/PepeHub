Конкретные задачи, зависимости и контрольные поставки — в [плане реализации аудиоплеера](docs/AUDIOBOOK_IMPLEMENTATION_PLAN.md).

Версия 0.5.0 добавляет несколько файлов одной аудиокниги, предпросмотр порядка и очередь воспроизведения. [Сценарий, изменения и ограничения](docs/AUDIOBOOK_MULTITRACK.md). Перенос базы 0.4 и резервные копии описаны в [журнале первого этапа](docs/AUDIOBOOK_PROGRESS.md).

- FB2/FB2.ZIP, TXT, Markdown, HTML, DOCX, RTF: импорт, извлечение текста, общая читалка и локальная позиция. PDF: отдельный нативный просмотрщик страниц с масштабированием. [Точная матрица форматов и ограничений](docs/FORMATS.md).
- EPUB: импорт с названием и авторами, главы в порядке spine, текстовое чтение по абзацам, размер шрифта 16–36, локальное восстановление главы/абзаца. Разбор в isolate, проверка CRC и лимитов распаковки. Исходник не изменяется.
- Flutter-клиент для Android/Windows: адаптивная библиотека, создание карточки, автор, формат, статус, поиск, фильтры и ручные сессии.
- Импорт MP3/M4B/M4A/AAC/OGG/Opus/FLAC/WAV: потоковое копирование в библиотеку, SHA-256, проверка размера/заголовка, защита от дубликатов. Исходник не изменяется; декодируемость проверяет плеер.
- Аудиоплеер: один или несколько файлов одной книги, список и автоматическая смена треков, перемотка ±15 секунд через границы файлов, скорость 0.5–3×, таймер сна, мини-плеер и восстановление локальной позиции издания/трека. В импорте — естественный порядок имён, ручная перестановка, прогресс и отмена.
- Автоматические сессии прослушивания по реальному активному времени, checkpoints каждые 10 секунд. Непереданные обновления объединяются; попытка отправки фиксирует неизменность операции для повторов.
- SQLite + Drift: локальные данные и очередь изменений сохраняются одной транзакцией; очередь переживает перезапуск.
- Кнопка синхронизации с API; ключ хранится через flutter_secure_storage. Проверка устройства, последовательная отправка и постраничное получение.
- Конфликты сохраняют локальную версию; можно оставить конфликт или принять серверную версию. Смена сервера/устройства после привязки базы пока не поддерживается.
- Worker API: авторизация отдельных устройств, изоляция владельцев, контроль ревизий, долговечные результаты операций, tombstones и отдельные подтверждения устройств.
- Локальный API использует настоящий обработчик Worker и SQLite, без аккаунта Cloudflare.
- Экспорт Markdown: файл через диалог Windows; на Android пока выделяемый текст для копирования.
- Чистый модуль обновления управляемых Markdown-блоков для будущего плагина Obsidian. Сохраняет окружающий текст и обнаруживает повреждённые маркеры.

**Это прототип.** EPUB пока отображается как текст по абзацам: без иллюстраций, CSS-вёрстки, сносок и DRM. Сессии чтения записываются вручную в библиотеке. Встроенные аудиоглавы, импорт папок, R2, облачная передача файлов и позиций, автоматическая фоновая синхронизация, полноценный плагин Obsidian и миграция Habit Timer пока не реализованы. Карточки и сессии уже синхронизируются; файлы и позиции локальные. Облачного развёртывания не было. Основной vault пользователя не изменялся.

## Локальный API

Требуется Node.js 24+. Из корня проекта:

```powershell
npm ci
npm test
npm run typecheck
npm run dev:api
```

API слушает `http://127.0.0.1:8787`. Первая команда запуска создаёт `.local/dev.sqlite` и `.local/devices.json` с двумя отдельными ключами одного локального владельца. Ключи не выводятся в журнал и исключены из Git. Файл предназначен только для локальной разработки; production provisioning требует отдельного административного механизма.

В настройках приложения укажите адрес API, `id` и `token` одной записи из `.local/devices.json`. На Android emulator адрес хоста — `http://10.0.2.2:8787`, использовать вторую запись устройства. Для реального телефона нужен доступный HTTPS-сервер; localhost телефона не является ПК.

## Flutter

При первоначальной реализации SDK загружен в `.tools/flutter`, пакеты — `.tools/pub-cache`. Эти каталоги не входят в исходники. Можно использовать собственный Flutter stable, совместимый с ограничениями `pubspec.yaml`.

Из корня проекта:

```powershell
$env:PUB_CACHE = "$PWD\.tools\pub-cache"
$env:CI = 'true'
Set-Location apps/pepehub
../../.tools/flutter/bin/flutter.bat pub get
../../.tools/flutter/bin/flutter.bat analyze --no-pub
../../.tools/flutter/bin/flutter.bat test --no-pub
../../.tools/flutter/bin/flutter.bat run -d windows --no-pub
```

Для глобального SDK заменить путь на `flutter`. Сквозной тест запускает отдельный Node-процесс на случайном loopback-порту с памятью SQLite, а не использует вашу рабочую базу.

### Windows

Требуются Visual Studio с **Desktop development with C++**, MSVC, CMake и Windows SDK. При реализации необходимые компоненты добавлены в установленную Visual Studio. Результаты сборки и нативных проверок фиксируются в `docs/VALIDATION.md`.

Если `pub get` скачал зависимости, но завершился ошибкой `Building with plugins requires symlink support`, можно включить Windows Developer Mode самостоятельно либо использовать локальные junction-ссылки без изменения системных настроек:

```powershell
# Из корня проекта, после pub get:
./scripts/prepare-windows.ps1
Set-Location apps/pepehub
../../.tools/flutter/bin/flutter.bat pub get
../../.tools/flutter/bin/flutter.bat build windows --no-pub
```

Скрипт создаёт только отсутствующие ссылки в сгенерированной папке Windows. Повторный успешный `pub get` после него обязателен: он завершает генерацию регистрации нативных плагинов. После обновления зависимостей Flutter может пересоздать этот каталог; тогда повторить подготовку и `pub get`. Скрипт не устанавливает C++ toolchain.

Нативный тест Windows создаёт собственный беззвучный WAV, проверяет декодер, перемотку и журнал; это не проверка всех вариантов MP3/M4B:

```powershell
../../.tools/flutter/bin/flutter.bat test integration_test/native_audio_test.dart -d windows --no-pub
```

## Облачный Worker

Код рассчитан на binding D1 `DB`. Конфигурация находится в `services/sync-worker/wrangler.jsonc`, начальная миграция — `migrations/0001_initial.sql`. `database_id` является явным placeholder. Для развёртывания потребуется создать отдельную D1, выполнить миграцию, настроить выдачу и отзыв ключей устройств, лимиты запросов и затем развернуть Worker. Текущие проверки выполнялись на SQLite-адаптере; поведение в workerd/D1 предстоит подтвердить перед production.
